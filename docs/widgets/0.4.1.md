# CoC Telegram 0.4.1: многопользовательская работа

## Что исправлено

В 0.4.0 общий Semaphore(1) задерживал все обычные команды, а HTTPXRequest по умолчанию имел только одно Telegram-соединение. Navigator и context.user_data связывали состояние с пользователем без чата. Создание Widget удаляло предыдущий, а claim менял revision до доставки Telegram: потерянный ответ делал кнопки устаревшими.

Теперь `SessionUpdateProcessor` выполняет работу по ключу `(chat_id, user_id)`. Внутри ключа порядок сохраняется, между ключами обработка параллельная. До 64 принятых обновлений и 20 одновременно работающих обработчиков; ожидание своей сессии не занимает рабочий слот. Пул HTTP Telegram — 24 соединения. Фоновые задания остаются заданиями PTB и не берут UI-lock. При превышении общей ёмкости очередь ожидает свободного места; не заявляется неограниченный параллелизм.

`SessionContext` разделяет незавершённые сценарии по чату. Navigator также разделяет экраны по чату/пользователю. Общие голосования и сохранённые составы остаются в существующих SQLite-таблицах. Конкурирующие правки состава защищены прежним CAS по revision, серверные проверки ролей сохранены.

## Доставка Widgets

Один владелец может иметь пять актуальных сообщений. Создание шестого удаляет самый старый экран, остальные работают независимо; TTL — 24 часа. Проверяются Telegram from.id, личный chat.id, message_id, token, revision и разрешённое сервером действие. Публичные данные Widget пустые.

`begin → prepare → editMessageWidgetData → delivered`: подготовленный payload сохраняется в SQLite; revision фиксируется после доставки. Если ответ потерялся, повторный запрос воспроизводит тот же payload, а не выполняет действие повторно. «Message is not modified» после повторной отправки считается успешной доставкой. Повтор административного перехода не запускает его второй раз. Резервирование незавершённого вычисления истекает через 15 секунд. Паузы SQLite выполняются в executor, с ограниченными повторными попытками, вне event loop.

Добавлены только поля pending/lease таблицы widget_screens. Пользовательские бизнес-таблицы не менялись. После рестарта доставка продолжается. При откате именно на 0.4.0 отключите widgets_enabled: его старый позиционный INSERT несовместим с дополнительными колонками; обычный интерфейс и бизнес-данные остаются доступны. /classic в 0.4.1 не требует миграций или удаления данных.

## Списки и производительность

Игроки клана, аккаунты, рейтинг КВ/ЛВК, донат и оставшиеся атаки: до 10 интерактивных строк. В каждой строке номер, имя, TH и основной показатель. Из списка открывается профиль, возврат сохраняет страницу. 45 игроков = 10/10/10/10/5. CWL показывает 8 кланов сразу. Длинные имена сокращаются явно многоточием по UTF-8 бюджету; список никогда молча не уменьшается до трёх. Длинные карточки героев/снаряжения и изменения развития имеют собственную пагинацию.

Один HTTP-клиент Widgets, до 4 запросов одновременно, кэш публичных данных 15 секунд/128 записей, одинаковые запросы объединяются. Ожидающих различных запросов не больше 128. Отмена одного клиента не отменяет общий запрос других клиентов. Возвращаются независимые копии данных. Backend объединяет одинаковые запросы CoC и расчёты /next-war, разрешает до 5 исходящих CoC-запросов одновременно. Формулы не менялись.

## Диагностика

В логах только операция и код: BACKEND_UNAVAILABLE, TELEGRAM_API_UNAVAILABLE, TELEGRAM_API_REJECTED, TELEGRAM_API_UNSUPPORTED, WIDGET_EXPIRED/STALE/BUSY, PERMISSION_DENIED, SQLITE_BUSY, TIMEOUT, STATE_ENCODING_ERROR. Никаких исключений, токенов, query payload или имён в этих строках. Ответ Telegram не позволяет достоверно отличить все ограничения клиента от отказа API; «unsupported» выделяется только по соответствующему ответу API. При неудаче открытия остаётся обычное меню; ошибка запроса сохраняет повтор/возврат и ссылку-команду /classic.

## Проверки

Локально: 122 bot + 60 backend + 5 add-on тестов. Новые сценарии используют Events/Barrier: 20 пользователей при заблокированном первом; две открываемые панели; личный/групповой чат; два Widget одного владельца; медленный Telegram; 502/504; SQLite contention; повтор доставки после рестарта; два руководителя меняют один состав; 10 разных профилей; 20 одинаковых анализов. 20 одинаковых запросов анализа дают один HTTP-запрос, максимум параллельных загрузок профилей — 4.

Локальная песочница запрещает socket wakeup из executor-thread: для локальных тестов применён внешний таймер пробуждения event loop в /tmp, без изменения приложения или тестов репозитория. GitHub Actions запускает обычный pytest без этой адаптации. На этом стенде максимальное время диспетчеризации 20 независимых пользователей при удерживаемом первом запросе составило 0,174 мс. Это время прохождения планировщика с готовыми mock-операциями, не задержка Telegram/CoC в production.

Отдельная CI-проверка `scripts/check_widget_layout.py`: Chromium, темы light/dark, ширина 320/390 px, 10 строк и 8 кланов, высота ≤600 px, без горизонтального выхода, работающее нажатие строки, UTF-8 ≤1024 и запрос ≤64 байт. Скриншоты публикуются как CI artifacts. Это макет TelegramWidget; он не заменяет проверку QuickJS, Android/iPhone и Raspberry Pi.

## Обновление

После одобрения PR и выпуска образа 0.4.1 обновить add-on штатно через Home Assistant. Сохранить обычную резервную копию. Значение widgets_enabled и секреты менять не требуется. /widgets открывает новую панель, /classic сохраняет обычный режим. PR не разворачивает production; существующий workflow main публикует образ после merge, поэтому merge является решением о выпуске.
